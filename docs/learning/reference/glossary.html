Reports, cases & audit

A one-page vocabulary for the reporting-and-cases design. Keep this open while reading the spec or a lesson.

The three layers

Report — evidence, frozen. Case (ticket) — work, moving. Audit log — accountability, append-only. Confusing these three is the most common reporting-system mistake.

Core terms

Report
An immutable snapshot of an entity dossier or a filtered query set, created by an analyst and exportable as CSV or XLSX. Spec §1, §6.1
Snapshot
The frozen JSON payload inside a report: summary, profile, timeline, up to 500 recent queries, intelligence, and provenance. It is never updated after insert. Spec §7
Immutability
The report's evidence fields cannot change. Only review fields (status, conclusion, verdict, reviewed_by, reviewed_at) may move. Reports are archived, never deleted. Spec §6.1, §10.1
Case (ticket)
A mutable work item that tracks an investigation from creation to closure: assignment, comments, evidence links, and an append-only timeline. "Ticket" is the everyday word; "case" is the data model. Spec §1, §6.2
Case event
One row in case_events: created, comment, status_changed, assigned, priority_changed, resolution_set, report_linked, report_unlinked. Events are appended, not edited. Spec §6.3
State machine
The rulebook of legal case states and transitions. An illegal move returns HTTP 409 with the list of allowed next states, rather than silently accepting a nonsense workflow. Spec §10.3
Transition
A permitted move from one case state to another, with a required permission and sometimes a required field (for example, resolving requires a resolution). Spec §10.3
Triage
Deciding whether a case is real work worth pursuing. In this design, open → triaged is the triage decision. Spec §10.3
Resolution
The outcome recorded when a case is resolved: true_positive, false_positive, benign, duplicate, or no_action. It is retained in history even after a reopen. Spec §6.2, §10.3
Verdict
The classification of an entity: Benign, Malicious, Review Needed, or Unknown. A report may carry an assessed verdict; that is not the same as changing the stored label. Spec §4 #5, §6.1
Label authority
The single path allowed to change a domain's stored label: POST /api/v1/daily-review/{domain}/verdict, with a required reason. Reviewing a report or resolving a case never changes the label. Spec §4 #5, §11.4
Audit log
A separate, append-only record of who did what, when, and to which target. Extended with target_type and target_id so report and case actions can be traced. Spec §6.5
Append-only
New facts are added as new rows; old facts are not rewritten. This is what makes the case timeline and the audit log trustworthy after a mistake or a disagreement. Spec §6.3, §6.5
Provenance
The list of evidence sources behind a report — local profile, query history, reputation, daily review, VT, OTX, DNS, RDAP — each with a timestamp. It answers "where did this claim come from?" Spec §7
Export
CSV or XLSX output of a report or query set. Exports are bounded (50,000 rows), formula-injection-safe, filter-parity with the screen, and audited with a REPORT_EXPORTED row. Spec §9

The six case states

State Plain meaning Allowed next Who can move it
open Created, not yet triaged triaged, closed cases:write; close needs cases:manage
triaged Accepted as real work investigating, awaiting_info, resolved, closed cases:write; close needs cases:manage
investigating Actively being worked awaiting_info, resolved, closed cases:write; close needs cases:manage
awaiting_info Blocked on more evidence investigating, resolved, closed cases:write; close needs cases:manage
resolved Finished, outcome recorded closed, investigating (reopen) cases:manage
closed Final, no further work investigating (reopen) cases:manage
Remember

resolved needs a resolution. closed needs cases:manage. Reopening clears closed_at but keeps the old resolution in the event history.
